# GitHub 测试 Skills 调研 — 对 ProbeFlow 有什么用

## 为什么要看这些项目

ProbeFlow 要做的是一个「能自动分析接口、生成用例、执行测试、分析失败」的 Agent 系统。**Agent 系统的核心难点不是写代码，而是提示词怎么设计、流程怎么控制、什么时候让 Agent 停、什么时候让 Agent 继续。**

GitHub 上这些项目已经在 Claude Code 里实战过这些问题了——他们的 skill 文件就是现成的「提示词 + 流程控制」参考。直接看他们怎么写，比自己从零摸索快。

以下只挑对我们最有用的 3 个项目，说清楚他们做了什么、哪部分对 ProbeFlow 有用。

---

## 一、diagnosing-bugs（Claude Code 内置 skill）→ 改进失败分析

### 它解决了什么问题

测试执行失败了，Agent 怎么分析原因？不能把日志一股脑丢给 LLM 让它自己看，那样效率低、结论不可靠。

### 核心做法

**第一条：先建反馈环，再想原因。** 90% 的价值在这一步。

> 不要一上来就「我觉得是 X 问题」。先搞一个能稳定复现失败的命令（curl、测试脚本），确定每次跑都能看到同样的失败。这个命令没搞出来之前，别往下走。

对我们 ProbeFlow 的意义：每次 EXECUTE_* 失败后，自动从 ExecutionRecord 生成一条 curl 命令，放进 Observation 里。这样后续不管是人工排查还是 Agent 分析，都有一个确定的复现入口。

**第二条：列出 3-5 个假设，排个序，再一个个验证。** 而且假设必须是可以被证伪的：

> 格式：「如果原因是 X，那么改变 Y 应该能让 bug 消失 / 改变 Z 应该能让它更糟」

对我们 ProbeFlow 的意义：深度失败分析（ANALYZE_FAILURE）的提示词可以直接用这个格式，让 Agent 先列假设再验证，而不是直接输出一个猜测结论。

### 对 ProbeFlow 的具体改动

```
现在: EXECUTE_* 失败 → Observation (一句话原因)
改为: EXECUTE_* 失败 → 自动生成 curl 复现命令 → BASIC Observation
      → 如果 Planner 触发深度分析 → 列出 3-5 个假设 → 逐个验证 → DEEP Observation
```

改动量：改 Observation 的数据结构和 ANALYZE_FAILURE 步骤的提示词即可。

## 二、correctless 的 11 项测试审计 → 改进断言质量

### 它解决了什么问题

生成了 100 条测试用例，但怎么知道这些用例的质量够不够？会不会只测了 happy path、漏了关键断言？

### 核心做法

每批测试用例生成完后，用一个独立 Agent 做 11 项检查。对我们最有用的 4 项：

| 检查项 | 什么意思 | ProbeFlow 怎么用 |
|---|---|---|
| 断言强度 | 是不是只断言了 HTTP 200？有没有检查返回体里的关键业务字段？ | CaseNormalizer 里加一个检查：如果所有断言都只是 statusCode，标 warning |
| Mock 间隙 | mock 掉的依赖，测试过了不代表真实环境能过 | ProbeFlow 是真发 HTTP 请求，这个问题不大，跳过 |
| 错误路径 | 只测了正常路径，没有测 401/403/422/500？ | 生成用例时，对每个接口至少生成 1 条鉴权失败 + 1 条参数校验失败的 case |
| Spec 覆盖 | 接口有 5 个必填参数，用例只覆盖了 3 个？ | 生成后对比 ApiSpec 的字段列表和 case 的 inputData，标出遗漏 |

### 对 ProbeFlow 的具体改动

在 CaseNormalizer 里加一个质量检查步骤（代码做，不调 LLM）：

```
对每条 TestCaseDraft:
1. 有 expectedStatusCode 吗？没有 → 拒绝 (已设计)
2. 断言只检查了 statusCode 吗？是 → 提示补业务字段断言
3. 有非 200 的 case 吗？没有 → 提示补异常路径
```

## 三、argus-qa Sentinel → 丰富用例生成角度

### 它解决了什么问题

生成用例时，Agent 容易只想到「正常输入→正常输出」。怎么让它系统性地从多个角度去想测试场景？

### 核心做法

Sentinel 不找 bug，它只问一个问题：**「这个代码/接口应该有哪些测试？」** 它从固定角度去逐个检查。

原文的 8 个维度包含性能、并发、CSRF 等，不适合纯 HTTP API 功能测试。精简为 **5 个角度**：

| # | 角度 | 关注点 |
|---|---|---|
| 1 | 正常路径 | 合法参数 → 预期成功响应 |
| 2 | 鉴权 | 无 Token、过期 Token、权限不足 |
| 3 | 参数校验 | 必填缺失、类型错误、边界值、超长、非法值 |
| 4 | 业务前置条件 | 订单未创建就支付、已退款订单再退款 |
| 5 | 响应结构 | 字段存在性、类型、业务状态码、错误信息格式 |

### 对 ProbeFlow 的具体改动

直接把 5 个角度写进 CaseGenerator 的提示词里，作为固定的检查清单：

```markdown
对每个 ApiSpec 生成用例时，必须覆盖以下角度：
- [ ] 正常路径（合法参数 → 预期成功）
- [ ] 鉴权（无 Token / 过期 Token / 权限不足）
- [ ] 参数校验（必填缺失 / 类型错误 / 边界值 / 超长 / 非法值）
- [ ] 业务前置条件（如订单必须先创建才能支付）
- [ ] 响应结构（字段存在性 / 类型 / 业务状态码 / 错误信息）
```

不需要独立 Agent——就是一个提示词段落，让生成用例时对照检查。

## 四、不需要现在做的

以下东西看起来很厉害但对 ProbeFlow 现阶段太重了，先不碰：

- **correctless 的 Agent 分离**（多个 Agent 互相审查）：ProbeFlow 目前是单 Agent 系统，搞多 Agent 协作需要改整个编排架构，V1 不值得
- **tdd-workflow 的 PreToolUse Hook**：用 bash hook 阻止 Agent 编辑文件。ProbeFlow 不是 IDE 插件，执行环境不一样
- **claude-code-mcp-qa-automation 的 flag-gated 配置**：22 个开关的 YAML 配置系统。ProbeFlow 现阶段直接改代码/配置就行，不需要这么重的开关系统
- **Sentinel 的 50 个工单自动生成**：把测试缺口生成 GitHub Issues。ProbeFlow 自己就是测试系统，不需要往外部 tracker 发工单

## 五、总结：改什么、不动什么

| 子系统 | 要改的 | 怎么改 | 不改的 |
|---|---|---|---|
| Observation (失败分析) | 深度分析提示词 | 加「先列 3-5 个假设再验证」的格式 | 基础归因逻辑不动 |
| CaseNormalizer (用例质量) | 质量检查步骤 | 加 3 项确定性检查（代码做，不调 LLM） | 去重逻辑不动 |
| CaseGenerator (用例生成) | 生成提示词 | 加 5 角度检查清单 | 生成链路不动 |
| 其他 6 个子系统 | 无 | — | 保持现有设计 |
