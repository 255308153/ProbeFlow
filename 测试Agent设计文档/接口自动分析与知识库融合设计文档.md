# 接口自动分析与知识库融合设计文档

## 1. 文档目标

本文档定义测试 Agent 在接口测试场景下的“自动接口分析能力”，以及如何结合知识库增强业务理解，从而提升测试用例生成与自动化接口测试的质量。

该模块的目标不是只做接口元数据提取，而是建立一套：

- 自动识别接口定义
- 自动补充业务上下文
- 自动生成测试洞察
- 自动服务后续编排与执行

的统一能力。

---

## 2. 问题背景

如果系统只依赖 OpenAPI 或手工录入，存在几个典型问题：

- 很多项目没有完整接口文档
- 文档和实际代码容易不一致
- 仅靠接口结构难以理解真实业务规则
- 仅靠代码又很难完全理解业务流程

因此，测试 Agent 需要把以下几类信息联合起来：

- 代码中的接口定义
- 文档中的接口资产
- 知识库中的业务流程与规则

只有这样，Agent 才不只是“知道接口长什么样”，还会“知道接口为什么存在，以及应该重点测什么”。

---

## 3. 总体设计思路

### 3.1 三层信息融合

接口自动分析建议基于三层信息融合：

```text
代码上下文
+ 接口资产
+ 业务知识库
-> Unified API Context
-> Test Insight
```

三层信息分别承担不同职责：

- 代码上下文：告诉 Agent 接口怎么实现
- 接口资产：告诉 Agent 接口怎么定义
- 业务知识库：告诉 Agent 接口在业务里起什么作用

### 3.2 统一目标

最终目标不是单纯产出一份路由列表，而是输出可供测试 Agent 使用的统一接口上下文对象。

该对象至少要支持：

- 生成接口测试用例
- 生成测试数据准备建议
- 生成关键断言建议
- 分析高风险业务场景
- 为执行与报告提供上下文

---

## 4. 核心输入来源

### 4.1 代码上下文

代码输入主要来自项目源码。

可识别信息包括：

- Controller / Route 定义
- 接口路径
- HTTP Method
- 请求参数
- 请求 DTO
- 返回 DTO
- 参数校验注解
- 鉴权注解
- Service 调用关系

在 Java Spring Boot 场景下，重点识别：

- `@RestController`
- `@RequestMapping`
- `@GetMapping`
- `@PostMapping`
- `@RequestParam`
- `@PathVariable`
- `@RequestBody`
- `@Validated`
- `@PreAuthorize`

### 4.2 接口资产

接口资产输入主要包括：

- OpenAPI / Swagger
- Postman Collection
- 手工录入的接口定义
- 历史测试用例
- 历史执行记录

这部分信息可以帮助系统快速拿到：

- 标准接口描述
- 请求示例
- 响应示例
- 既有测试资产

### 4.3 业务知识库

业务知识库输入主要包括：

- PRD
- 业务流程文档
- FAQ
- 业务规则说明
- 事故复盘
- 测试规范
- 项目知识文档

知识库在这里的主要作用是补充：

- 接口所处业务流程
- 业务前置条件
- 上下游依赖
- 核心业务约束
- 风险场景

---

## 5. 核心模块设计

### 5.1 Code Import Analyzer

负责从代码中自动发现接口定义。

职责：

- 扫描代码目录
- 识别 Web 框架类型
- 定位接口入口类和方法
- 抽取 path / method / 参数 / 返回对象
- 分析校验和鉴权注解

输出结果建议为：

- `ApiSpecDraft`
- `CodeContext`

### 5.2 Framework Detector

负责识别当前项目所使用的后端框架。

第一版建议优先支持：

- `Java Spring Boot`

后续可扩展：

- Express
- FastAPI
- Django
- Gin
- NestJS

这个模块的意义在于，不同框架的接口抽取规则完全不同，需要先识别框架再走不同提取流程。

### 5.3 Route Extractor

负责从代码中抽取接口路由信息。

核心输出：

- 接口路径
- HTTP Method
- Controller 名称
- Handler 方法名

这是整个代码导入链路中最基础的一层。

### 5.4 Request / Response Model Extractor

负责抽取请求与响应模型。

可抽取内容：

- Query 参数
- Path 参数
- Header 参数
- Body DTO
- 返回值对象
- 字段类型
- 字段注释
- 是否必填

这部分信息直接影响测试用例生成质量。

### 5.5 Validation / Auth Extractor

负责抽取接口级约束信息。

可抽取内容：

- 参数校验规则
- 非空校验
- 长度限制
- 枚举约束
- 鉴权要求
- 角色限制
- Token/Header 要求

这部分对生成异常测试场景非常关键。

### 5.6 Service Context Analyzer

负责进一步分析接口背后的业务上下文。

可分析内容：

- 调用了哪些 Service
- 是否存在关键分支
- 是否涉及数据库写操作
- 是否依赖外部服务
- 是否有状态变更

如果后续接入 `codegraph`，这个模块会更强。

### 5.7 Knowledge Retriever

负责从知识库中召回与当前接口最相关的业务材料。

召回目标包括：

- 业务流程说明
- 规则说明
- 风险说明
- 常见问题说明
- 历史事故复盘

它的本质作用是让接口分析不只停留在代码结构层。

### 5.8 Business Flow Analyzer

负责将知识库内容转化成接口的业务语义上下文。

可输出内容：

- 所属业务流程
- 前置依赖
- 下游影响
- 关键业务规则
- 高风险场景

这一步是从“知识文档”走向“测试可用信息”的关键转换。

### 5.9 API Context Merger

负责把代码分析结果、接口资产和知识库结果融合成统一上下文。

主要职责：

- 合并多源信息
- 处理冲突信息
- 选择更可信来源
- 输出统一 `UnifiedApiContext`

### 5.10 Test Insight Generator

负责基于统一接口上下文生成测试洞察。

可输出内容：

- 推荐测试点
- 关键正常场景
- 关键异常场景
- 前置数据准备建议
- 核心断言建议
- 风险优先级

---

## 6. 推荐分析流程

建议整体分析流程如下：

```text
上传代码 / 指定仓库目录
-> Framework Detector
-> Route Extractor
-> Request / Response Model Extractor
-> Validation / Auth Extractor
-> Service Context Analyzer
-> 知识库检索
-> Business Flow Analyzer
-> API Context Merger
-> UnifiedApiContext
-> Test Insight Generator
```

---

## 7. 统一输出对象设计

建议至少定义以下几个统一对象：

### 7.1 ApiSpec

用于表达接口的结构定义。

建议包含：

- 路径
- 方法
- 参数定义
- 请求模型
- 响应模型
- 鉴权要求

### 7.2 ApiBusinessContext

用于表达接口的业务语义上下文。

建议包含：

- 所属业务流程
- 前置条件
- 下游影响
- 业务规则
- 风险点

### 7.3 ApiTestInsight

用于表达测试分析结果。

建议包含：

- 推荐测试点
- 异常场景建议
- 测试数据建议
- 核心断言建议
- 风险优先级

### 7.4 UnifiedApiContext

用于表达最终合并后的接口上下文。

建议包含：

- `apiSpec`
- `codeContext`
- `businessContext`
- `testInsight`
- `sourceRefs`

## 8. codegraph 的作用

在本模块中，`codegraph` 很适合承担代码结构理解层的能力。

推荐用途：

- 查找 controller 到 service 的调用链
- 快速定位接口相关 DTO / service / repository
- 做结构化代码检索
- 辅助 Agent 构建接口代码上下文

需要明确的是：

- `codegraph` 不是业务知识库
- `codegraph` 不是接口文档替代品
- `codegraph` 更适合做代码理解与上下文定位器

在这个设计里，它最适合放在：

- `Service Context Analyzer`
- `Code Import Analyzer`

---

## 9. 对测试 Agent 的价值

接口自动分析和知识库融合能力，会让测试 Agent 从“会解析接口”升级为“理解接口该怎么测”。

它能直接增强以下能力：

- 自动生成更准确的接口测试用例
- 自动补充异常场景
- 自动生成更贴近业务的断言
- 自动识别高风险流程
- 自动补充前置依赖与测试数据要求

一句话总结就是：

`代码告诉 Agent 接口怎么写，知识库告诉 Agent 接口为什么存在、应该重点测什么。`

## 10. 第一版落地建议

第一版建议聚焦，不要一开始做多语言全框架支持。

### 10.1 第一版建议范围

- 支持 `Java Spring Boot`
- 支持上传代码目录或仓库
- 支持结合知识库做业务上下文召回
- 统一输出 `UnifiedApiContext`

### 10.2 第一版优先能力

- 自动识别 Controller
- 自动提取 path / method
- 自动提取请求参数与 DTO
- 自动提取返回对象
- 自动提取校验与鉴权注解
- 自动召回业务流程文档
- 自动生成基础测试洞察

### 10.3 第一版暂不追求

- 多语言框架通吃
- 复杂跨服务全链路自动还原
- 极高精度的业务语义自动理解

第一版重点是先跑通：

`代码导入 + 知识库召回 + 统一上下文构建 + 测试洞察生成`

## 11. 与其他模块的关系

### 11.1 与工具编排系统

该模块为编排系统提供：

- 接口分析结果
- 测试洞察
- 上下文构建输入

### 11.2 与记忆系统

该模块可从记忆系统获取：

- 历史接口测试经验
- 常见失败模式
- 项目级规则知识

### 11.3 与测试用例生成系统

该模块为用例生成提供：

- 接口结构定义
- 业务流程上下文
- 风险点分析
- 测试点建议

---

## 12. 一句话总结

接口自动分析模块不应只做“接口抽取器”，而应做成一个融合代码、文档和知识库的统一上下文构建器。

最终形态可以概括为：

`代码自动分析 + 知识库业务理解 + UnifiedApiContext + Test Insight`
