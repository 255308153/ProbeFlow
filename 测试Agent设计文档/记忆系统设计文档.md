# 记忆系统设计文档

## 1. 文档目标

本文档定义测试 Agent 的记忆系统设计方案，用于支撑以下核心能力：

- 保存当前会话中的短期上下文
- 保存当前任务中的持续状态与执行结果
- 提炼跨任务可复用的测试经验
- 为编排系统按需构建统一上下文

这套设计借鉴两种核心思想：

- `Mem0` 的记忆提纯
- `Viking` 的统一上下文

整体目标不是“把所有信息都存下来”，而是建立一套 `可沉淀、可提炼、可召回、可装配` 的记忆体系。

---

## 2. 设计原则

### 2.1 不是全量存储，而是分层存储

并不是所有信息都适合进入长期记忆。

记忆系统应当按价值和生命周期分层：

- 短期会话信息放短期层
- 当前任务事实放任务层
- 跨任务经验放长期层
- 团队规范放共享知识层

### 2.2 不是直接写库，而是先提纯再写入

原始会话、原始工具输出、原始错误日志通常噪音很大。

因此长期记忆不应直接保存原始内容，而应该经过：

- 抽取
- 分类
- 去重
- 合并
- 压缩

之后再写入。

### 2.3 不是全量召回，而是按需组装上下文

记忆的读取目标不是“把历史全塞给模型”，而是“给当前任务取最相关的一小部分”。

因此系统必须有统一上下文构建能力。

### 2.4 记忆系统服务于任务闭环

记忆系统不是一个独立的知识库产品，而是测试 Agent 的基础能力。

它要直接服务于：

- 用例生成
- 接口执行
- 失败分析
- 经验复用
- 结果补充

---

## 3. 总体架构

### 3.1 记忆层次划分

记忆系统建议拆成五层：

- `Session Memory`
- `Task Memory`
- `Memory Refinery`
- `Refined Long-term Memory`
- `Unified Context Builder`

可选补充一层：

- `Team Knowledge Memory`

### 3.2 总体数据流

```text
Conversation / Tool Results / Task Execution
-> Session Memory / Task Memory
-> Memory Refinery
-> Refined Long-term Memory
-> Unified Context Builder
-> Current Agent Context
```

---

## 4. 核心模块设计

### 4.1 Session Memory

Session Memory 用于保存当前会话中的短期上下文。

它主要解决的问题是：

- 当前这一轮在做什么
- 最近几轮已经得出了哪些结论
- 最近一次工具调用发生了什么
- 最近一次失败是因为什么

建议保存内容：

- 当前任务目标
- 最近对话中的关键结论
- 最近执行的工具摘要
- 最近一次失败原因
- 当前阶段的中间决策

特点：

- 生命周期短
- 更新频繁
- 强时效性
- 不要求长期保留

### 4.2 Task Memory

Task Memory 用于保存当前任务对象的持续状态和事实信息。

这是测试 Agent 中最重要的记忆层之一，因为一个测试任务经常是多轮推进的。

建议保存内容：

- 任务基础信息
- 需求摘要
- OpenAPI / 接口摘要
- 已生成测试用例
- 已执行接口记录
- 断言结果
- 失败样本
- 已做过的分析结论
- 下一步建议

特点：

- 生命周期覆盖整个任务
- 强结构化
- 可追踪
- 可支持任务恢复与断点续跑

### 4.3 Memory Refinery

Memory Refinery 是整个系统的“记忆提纯层”，借鉴 Mem0 的核心思路。

它的职责不是简单存储，而是负责识别哪些信息值得沉淀成长期经验。

主要职责：

- 从 Session / Task 中抽取高价值信息
- 按类型做分类
- 去重与合并相似经验
- 压缩冗余描述
- 过滤一次性信息与低价值噪音

适合提纯的信息：

- 某类接口常见断言模板
- 某项目特殊鉴权方式
- 某类失败的高频根因
- 某领域的边界测试策略
- 用户的输出偏好与测试风格

不适合直接提纯的内容：

- 一次性报错日志全文
- 原始大段对话
- 临时中间推理
- 与任务无关的低价值输出

### 4.4 Refined Long-term Memory

这是经过提纯后的长期记忆库。

它的目标是保存“跨任务仍然有价值”的经验，而不是保存原始历史。

建议分类：

- `project_knowledge`
- `testing_pattern`
- `failure_pattern`
- `preference`
- `domain_rule`

每条长期记忆建议至少包含：

- 记忆类型
- 标题
- 摘要
- 适用范围
- 来源任务
- 触发条件
- 检索标签
- 最近使用时间

特点：

- 强复用性
- 可检索
- 可持续演化
- 可被后续任务按需召回

### 4.5 Unified Context Builder

Unified Context Builder 借鉴 Viking 的“统一上下文”思想，是整个系统的读路径核心。

它的职责不是简单搜索，而是根据当前任务需要，从多个来源按需组装上下文。

可组合的来源包括：

- Session Memory
- Task Memory
- Refined Long-term Memory
- Team Knowledge Memory
- 当前外部材料

它要解决的问题是：

- 这次生成测试用例需要哪些历史测试模式
- 这次执行接口测试需要哪些环境知识
- 这次分析失败需要哪些项目经验

输出建议统一封装为 `ContextBundle`。

### 4.6 Team Knowledge Memory

这是一个可选层，用来承载团队共享的、人工可维护的知识。

建议使用 Markdown / Docs 形态维护。

适合保存：

- 团队测试规范
- 环境说明
- 某项目特殊接口规则
- 事故复盘
- 业务领域说明

这一层的价值在于：

- 人可维护
- 团队可共享
- 对 Agent 可检索

## 5. 写路径设计

### 5.1 写入来源

记忆系统的写入来源主要有：

- 用户对话
- 工具调用结果
- 测试执行结果
- 失败分析结果
- 最终任务结论

### 5.2 写入流程

建议写入流程如下：

```text
Raw Input
-> Session / Task Memory
-> Memory Candidate Extraction
-> Memory Refinery
-> Refined Long-term Memory
```

### 5.3 写入规则

建议遵循以下规则：

- 当前轮强相关内容优先写 Session Memory
- 当前任务事实优先写 Task Memory
- 只有跨任务仍有价值的信息才进入 Long-term Memory
- 团队规范类信息写 Team Knowledge，而不是自动长期记忆

---

## 6. 读路径设计

### 6.1 读路径目标

读路径的目标是为当前步骤构造“刚好够用”的上下文，而不是最大化召回。

### 6.2 读取流程

建议读取流程如下：

```text
Current Task / Step
-> Context Query
-> Unified Context Builder
-> Load Session Memory
-> Load Task Memory
-> Retrieve Long-term Memory
-> Merge Team Knowledge
-> Build ContextBundle
```

### 6.3 读取策略

建议读取时遵循：

- 优先取 Task Memory，因为与当前任务最直接相关
- Session Memory 用于保留最近轮次决策痕迹
- Long-term Memory 只按标签、类型、触发条件召回相关片段
- Team Knowledge 只在当前任务涉及该项目/规范时引入

---

## 7. 长期记忆提纯策略

### 7.1 提纯判断标准

以下信息适合进入长期记忆：

- 跨任务可复用
- 对后续决策有帮助
- 能归纳成稳定模式
- 能被标签化和检索

以下信息不适合进入长期记忆：

- 一次性偶发日志
- 与任务目标无关的上下文
- 无法泛化的临时对话
- 太细碎、太底层、没有复用价值的信息

### 7.2 提纯动作

对候选记忆建议执行以下动作：

- `extract`
- `classify`
- `deduplicate`
- `merge`
- `compress`
- `tag`

### 7.3 提纯结果示例

原始输入：

`用户项目中的支付接口在测试环境下，签名字段 sign 必须放在最后一个参数，否则接口会返回 401。`

提纯后长期记忆：

- type: `project_knowledge`
- title: `支付接口签名字段顺序约束`
- summary: `支付相关接口在测试环境中要求 sign 字段位于最后，否则可能返回 401。`
- tags: `payment`, `signature`, `test-env`, `401`

## 9. 存储选型建议

### 9.1 Session Memory

建议使用：

- `Redis`
- 或本地缓存，如 `Caffeine`

适合原因：

- 高读写频率
- 生命周期短
- 适合设置 TTL

### 9.2 Task Memory

建议使用：

- `PostgreSQL`

适合原因：

- 强结构化
- 易于按任务查询
- 便于任务恢复

### 9.3 Long-term Memory

建议使用：

- `PostgreSQL + pgvector`

适合原因：

- 可以同时支持结构化字段检索和向量召回
- 适合中期规模的平台型产品

### 9.4 Team Knowledge

建议使用：

- `Markdown 文档`
- `项目知识库`

适合原因：

- 人可编辑
- 团队可维护
- 可逐步接入检索层

## 10. 与编排系统的配合方式

记忆系统和编排系统之间建议通过明确边界协作。

### 10.1 编排系统调用记忆系统

编排系统需要：

- 在每一轮开始前构建上下文
- 在每一步执行后写入结果
- 在失败分析后沉淀经验

### 10.2 记忆系统为编排提供能力

记忆系统主要提供三种能力：

- `loadContext(taskId, stepType)`
- `writeTaskMemory(taskId, observation)`
- `refineAndPersist(memoryCandidates)`

### 10.3 推荐协作闭环

```text
Orchestration Step Execution
-> Observation
-> Task Memory Write
-> Memory Candidate Extraction
-> Memory Refinery
-> Long-term Memory Persist
-> Next Step Context Retrieval
```

## 11. Java 第一版落地建议

建议模块拆分如下：

```text
com.xxx.agent.memory.session
com.xxx.agent.memory.task
com.xxx.agent.memory.longterm
com.xxx.agent.memory.refinery
com.xxx.agent.memory.context
com.xxx.agent.memory.model
com.xxx.agent.memory.repository
```

建议第一版优先实现的接口：

- `SessionMemoryService`
- `TaskMemoryService`
- `LongTermMemoryService`
- `MemoryRefineryService`
- `UnifiedContextBuilder`

建议第一版先支持的能力：

- 写入 Session Memory
- 写入 Task Memory
- 生成 Long-term Memory Candidate
- 从多层记忆组装 ContextBundle

第一版不必一开始就做得太复杂，不需要先追求自动化提纯的极致准确率，先保证：

- 结构清晰
- 可查询
- 可回写
- 可扩展

---

## 12. 一句话总结

记忆系统的核心不是“多存”，而是“分层存、提纯存、按需取”。

最终方案可以概括为：

`Session Memory + Task Memory + Mem0 风格 Memory Refinery + Refined Long-term Memory + Viking 风格 Unified Context Builder`
