# 记忆系统设计文档

## 1. 文档目标

本文档定义测试 Agent 的记忆系统设计方案，用于支撑以下核心能力：

- 保存当前会话中的短期上下文
- 保存当前任务中的持续状态与执行结果
- 提炼跨任务可复用的测试经验
- 为编排系统按需构建统一上下文

这套设计借鉴两种核心思想：

- `Mem0` 的记忆提纯
- `Viking` 的统一上下文

整体目标不是“把所有信息都存下来”，而是建立一套 `可沉淀、可提炼、可召回、可装配` 的记忆体系。

---

## 2. 设计原则

### 2.1 不是全量存储，而是分层存储

并不是所有信息都适合进入长期记忆。

记忆系统应当按价值和生命周期分层：

- 短期会话信息放短期层
- 当前任务事实放任务层
- 跨任务经验放长期层
- 团队规范放共享知识层

### 2.2 不是直接写库，而是先提纯再写入

原始会话、原始工具输出、原始错误日志通常噪音很大。

因此长期记忆不应直接保存原始内容，而应该经过：

- 抽取
- 分类
- 去重
- 合并
- 压缩

之后再写入。

### 2.3 不是全量召回，而是按需组装上下文

记忆的读取目标不是“把历史全塞给模型”，而是“给当前任务取最相关的一小部分”。

因此系统必须有统一上下文构建能力。

### 2.4 记忆系统服务于任务闭环

记忆系统不是一个独立的知识库产品，而是测试 Agent 的基础能力。

它要直接服务于：

- 用例生成
- 接口执行
- 失败分析
- 经验复用
- 结果补充

---

## 3. 总体架构

### 3.1 记忆层次划分

记忆系统建议拆成五层：

- `Session Memory`
- `Task Memory`
- `Memory Refinery`
- `Refined Long-term Memory`
- `Unified Context Builder`

可选补充一层：

- `Team Knowledge Memory`

### 3.2 总体数据流

```text
Conversation / Tool Results / Task Execution
-> Session Memory / Task Memory
-> Memory Refinery
-> Refined Long-term Memory
-> Unified Context Builder
-> Current Agent Context
```

## 4. 核心模块设计

### 4.1 Session Memory

Session Memory 用于保存当前会话中的短期上下文。

它主要解决的问题是：

- 当前这一轮在做什么
- 最近几轮已经得出了哪些结论
- 最近一次工具调用发生了什么
- 最近一次失败是因为什么

建议保存内容：

- 当前任务目标
- 最近对话中的关键结论
- 最近执行的工具摘要
- 最近一次失败原因
- 当前阶段的中间决策

特点：

- 生命周期短
- 更新频繁
- 强时效性
- 不要求长期保留

### 4.2 Task Memory

Task Memory 用于保存当前任务对象的持续状态和事实信息。

这是测试 Agent 中最重要的记忆层之一，因为一个测试任务经常是多轮推进的。

建议保存内容：

- 任务基础信息
- 需求摘要
- OpenAPI / 接口摘要
- 已生成测试用例
- 已执行接口记录
- 断言结果
- 失败样本
- 已做过的分析结论
- 下一步建议

特点：

- 生命周期覆盖整个任务
- 强结构化
- 可追踪
- 可支持任务恢复与断点续跑

### 4.3 Memory Refinery

Memory Refinery 是整个系统的“记忆提纯层”，借鉴 Mem0 的核心思路。

它的职责不是简单存储，而是负责识别哪些信息值得沉淀成长期经验。

主要职责：

- 从 Session / Task 中抽取高价值信息
- 按类型做分类
- 去重与合并相似经验
- 压缩冗余描述
- 过滤一次性信息与低价值噪音

适合提纯的信息：

- 某类接口常见断言模板
- 某项目特殊鉴权方式
- 某类失败的高频根因
- 某领域的边界测试策略
- 用户的输出偏好与测试风格

不适合直接提纯的内容：

- 一次性报错日志全文
- 原始大段对话
- 临时中间推理
- 与任务无关的低价值输出

### 4.4 Refined Long-term Memory

这是经过提纯后的长期记忆库。

它的目标是保存“跨任务仍然有价值”的经验，而不是保存原始历史。

建议分类：

- `project_knowledge`
- `testing_pattern`
- `failure_pattern`
- `preference`
- `domain_rule`

每条长期记忆建议至少包含：

- 记忆类型
- 标题
- 摘要
- 适用范围
- 来源任务
- 触发条件
- 检索标签
- 最近使用时间

特点：

- 强复用性
- 可检索
- 可持续演化
- 可被后续任务按需召回

### 4.5 Unified Context Builder

Unified Context Builder 借鉴 Viking 的“统一上下文”思想，是整个系统的读路径核心。

它的职责不是简单搜索，而是根据当前任务需要，从多个来源按需组装上下文。

可组合的来源包括：

- Session Memory
- Task Memory
- Refined Long-term Memory
- Team Knowledge Memory
- 当前外部材料

它要解决的问题是：

- 这次生成测试用例需要哪些历史测试模式
- 这次执行接口测试需要哪些环境知识
- 这次分析失败需要哪些项目经验

输出建议统一封装为 `ContextBundle`。

### 4.6 Team Knowledge Memory

这是一个可选层，用来承载团队共享的、人工可维护的知识。

建议使用 Markdown / Docs 形态维护。

适合保存：

- 团队测试规范
- 环境说明
- 某项目特殊接口规则
- 事故复盘
- 业务领域说明

这一层的价值在于：

- 人可维护
- 团队可共享
- 对 Agent 可检索

## 5. 写路径设计

### 5.1 写入来源

记忆系统的写入来源主要有：

- 用户对话
- 工具调用结果
- 测试执行结果
- 失败分析结果
- 最终任务结论

### 5.2 写入流程

建议写入流程如下：

```text
Raw Input
-> Session / Task Memory
-> Memory Candidate Extraction
-> Memory Refinery
-> Refined Long-term Memory
```

### 5.3 写入规则

建议遵循以下规则：

- 当前轮强相关内容优先写 Session Memory
- 当前任务事实优先写 Task Memory
- 只有跨任务仍有价值的信息才进入 Long-term Memory
- 团队规范类信息写 Team Knowledge，而不是自动长期记忆

---

## 6. 读路径设计

### 6.1 读路径目标

读路径的目标是为当前步骤构造“刚好够用”的上下文，而不是最大化召回。

### 6.2 读取流程

建议读取流程如下：

```text
Current Task / Step
-> Context Query
-> Unified Context Builder
-> Load Session Memory
-> Load Task Memory
-> Retrieve Long-term Memory
-> Merge Team Knowledge
-> Build ContextBundle
```

### 6.3 读取策略

建议读取时遵循：

- 优先取 Task Memory，因为与当前任务最直接相关
- Session Memory 用于保留最近轮次决策痕迹
- Long-term Memory 只按标签、类型、触发条件召回相关片段
- Team Knowledge 只在当前任务涉及该项目/规范时引入

---

## 7. 长期记忆提纯策略

### 7.1 提纯判断标准

以下信息适合进入长期记忆：

- 跨任务可复用
- 对后续决策有帮助
- 能归纳成稳定模式
- 能被标签化和检索

以下信息不适合进入长期记忆：

- 一次性偶发日志
- 与任务目标无关的上下文
- 无法泛化的临时对话
- 太细碎、太底层、没有复用价值的信息

### 7.2 提纯动作

对候选记忆建议执行以下动作：

- `extract`
- `classify`
- `deduplicate`
- `merge`
- `compress`
- `tag`

### 7.3 提纯结果示例

原始输入：

`用户项目中的支付接口在测试环境下，签名字段 sign 必须放在最后一个参数，否则接口会返回 401。`

提纯后长期记忆：

- type: `project_knowledge`
- title: `支付接口签名字段顺序约束`
- summary: `支付相关接口在测试环境中要求 sign 字段位于最后，否则可能返回 401。`
- tags: `payment`, `signature`, `test-env`, `401`

## 9. 存储选型建议

### 9.1 Session Memory

建议使用：

- `Redis`
- 或本地缓存，如 `Caffeine`

适合原因：

- 高读写频率
- 生命周期短
- 适合设置 TTL

### 9.2 Task Memory

建议使用：

- `PostgreSQL`

适合原因：

- 强结构化
- 易于按任务查询
- 便于任务恢复

### 9.3 Long-term Memory

建议使用：

- `PostgreSQL + pgvector`

适合原因：

- 可以同时支持结构化字段检索和向量召回
- 适合中期规模的平台型产品

### 9.4 Team Knowledge

建议使用：

- `Markdown 文档`
- `项目知识库`

适合原因：

- 人可编辑
- 团队可维护
- 可逐步接入检索层

## 10. 与编排系统的配合方式

记忆系统和编排系统之间建议通过明确边界协作。

### 10.1 编排系统调用记忆系统

编排系统需要：

- 在每一轮开始前构建上下文
- 在每一步执行后写入结果
- 在失败分析后沉淀经验

### 10.2 记忆系统为编排提供能力

记忆系统主要提供三种能力：

- `loadContext(taskId, stepType)`
- `writeTaskMemory(taskId, observation)`
- `refineAndPersist(memoryCandidates)`

### 10.3 推荐协作闭环

```text
Orchestration Step Execution
-> Observation
-> Task Memory Write
-> Memory Candidate Extraction
-> Memory Refinery
-> Long-term Memory Persist
-> Next Step Context Retrieval
```

## 12. 一句话总结

记忆系统的核心不是“多存”，而是“分层存、提纯存、按需取”。

最终方案可以概括为：

`Session Memory + Task Memory + Mem0 风格 Memory Refinery + Refined Long-term Memory + Viking 风格 Unified Context Builder`

## 13. V5-2 Memory Fact Pipeline

V5-2 把长期记忆写路径从“候选文本压缩”升级为“事实提纯”。它要解决的问题不是怎么多存日志，而是怎么让 Agent 从执行经验里学到可复用、可解释、可追溯的事实。

完整写路径如下：

```text
Agent Memory Candidate
-> Sanitization
-> Fact Extraction
-> Classification
-> Quality Gate
-> Dedup / Merge / Conflict Check
-> Evidence Ledger
-> Long-term Memory
-> Embedding
-> Unified Context
```

这条链路的核心入口仍然是 `MemoryRefineryService`。失败分析、StepOutcome、人工决策、Policy Learning、Suite Failure 等来源可以通过 Agent Memory Feedback 形成候选，但不能绕过事实提纯直接写 `LongTermMemory`。

### 13.1 与 mem0 / Viking 的关系

ProbeFlow 借鉴 mem0 的记忆提纯思想：写入长期记忆前先做 extract、classify、dedup、merge、score、store，而不是把对话、日志、工具输出全文塞进长期记忆。

但 ProbeFlow 不引入 mem0 SDK，也不把运行时绑定到 mem0。原因是接口测试 Agent 的事实身份、证据账本、错误码、接口路径、SUITE 变量依赖等规则强依赖 ProbeFlow 自己的领域模型，直接套 SDK 很难讲清这些工程边界。

ProbeFlow 也借鉴 Viking 的统一上下文思想：Memory、RAG、Task State、ApiSpec 最终都应该进入统一上下文，让 Planner、用例生成、失败分析消费同一套可解释材料。

但 V5-2 不引入 VikingDB。V5-2 的重点是 Memory 写路径和事实质量，底层存储继续使用现有 `LongTermMemory`、V5-1 embedding profile 和 pgvector 召回地基。

### 13.2 Memory Fact 合同

`MemoryFact` 是候选进入长期记忆前的中间领域对象，不等同于最终持久化实体。它表达“这条候选里真正值得长期保存的事实是什么”。

核心字段包括：

- `factType`：事实类型。
- `summary` / `content` / `fullContent`：摘要、规范化内容和可解释证据文本。
- `applicability`：适用范围，例如 system、module、apiPath、errorCode。
- `trigger`：什么时候应该使用这条记忆。
- `tags`：用于检索和合并的标签。
- `identityHints`：事实身份线索，例如 systemName、module、apiPath、httpMethod、errorCode、businessEntity。
- `evidenceEntries`：来源证据，包含 sourceType、sourceRef、taskId、sanitizedEvidence。
- `confidence` / `importance` / `reuseScore`：可信度、重要性、复用价值。
- `qualityStatus` / `rejectionReason`：质量门禁结果。
- `fingerprint`：事实指纹，用于去重合并。

V5-2 覆盖的主要 fact type：

- `failure_pattern`：高频失败根因或恢复经验。
- `testing_pattern`：接口、字段、状态流转的测试策略。
- `project_knowledge`：项目级稳定规则，例如鉴权、租户、模块、错误码语义。
- `preference`：用户或团队对输出、用例、报告的偏好。
- `policy_learning`：Planner / Policy Validator 从拒绝、放行、人工审批中学到的安全经验。
- `suite_dependency_fact`：SUITE 链路中上游步骤、变量提取、下游消费之间的稳定关系。
- `variable_extraction_fact`：响应字段可作为后续变量的经验。
- `business_precondition_fact`：链路执行前必须满足的状态、数据或权限条件。

### 13.3 Quality Gate 防污染

Quality Gate 是防止 memory pollution 的第一道硬边界。它拒绝以下候选：

- 空候选。
- 置信度过低。
- 一次性报错或临时调试信息。
- 只适用于当前任务的 task-local 信息。
- 没有可复用事实。
- 没有证据来源。
- 太泛、无法指导后续任务的结论。
- 原始日志、堆栈、敏感 header、token、密码等污染内容。
- 与已有长期记忆存在关键身份冲突的相似事实。

这意味着“记住这次失败”“注意一下”“这个任务临时这样处理”不会进入长期记忆。长期记忆只保存跨任务仍有复用价值的事实。

### 13.4 去重、合并与证据账本

V5-2 的去重不是简单比较 summary / content。它综合：

- exact source idempotency：同一 `sourceType + sourceRef + taskId` 重放时保持幂等。
- fact fingerprint：同一事实指纹优先合并。
- identity hints：system、module、apiPath、httpMethod、errorCode、businessEntity 等必须一致。
- source hints、tags、evidence hash、文本相似度。

同一事实从不同来源再次出现时，系统会合并到已有 `LongTermMemory`，而不是新增重复记录。合并会更新：

- `evidenceCount`：支撑这条记忆的证据数量。
- `mergeCount`：这条事实被增强的次数。
- `mergedSourceRefs` / `mergedSourceTypes`：它由哪些来源支撑。
- `evidenceLedger` / `evidenceSummaries`：可解释证据账本。
- `confidence` / `importance` / `successContribution`：随着重复证据、人类确认、高风险故障等因素有限增强。
- embedding：合并后内容变化，需要重新生成 embedding，让 pgvector 召回使用最新事实。

这些字段让长期记忆能回答“它从哪里来、为什么可信、被合并过几次、由哪些执行证据支撑”。

### 13.5 Identity Conflict Guard

相似文本不等于同一事实。接口测试场景里，错误码、接口路径、业务实体一旦混淆，长期记忆会变成误导。

因此 V5-2 引入 identity conflict guard。可比较候选如果存在关键身份冲突，不能合并，也不能覆盖已有记忆。典型例子：

- `systemName=billing` 的经验不能合并到 `systemName=warehouse`。
- `module=payment` 的 timeout 经验不能合并到 `module=refund`。
- `/api/payments/charge` 的规则不能合并到 `/api/refunds/create`。
- `errorCode=GW_TIMEOUT` 不能合并到 `errorCode=AUTH_401`。
- `businessEntity=order` 不能合并到 `businessEntity=inventory`。

冲突候选会返回 `identity-conflict`，并在 audit summary 中说明冲突字段、已有值、候选值和已有 memory id，方便排查。

### 13.6 Deterministic 与 LLM-assisted Extractor

默认 extractor 是 deterministic。它基于候选来源、文本、metadata、tags 做稳定分类和字段提取，保证本地与 CI 的默认 `mvn test` 不需要真实 LLM key、真实 embedding 服务或外部网络。

LLM-assisted extractor 只是显式启用的扩展点。启用时必须通过配置选择 `probeflow.memory.fact-extractor.mode=llm-assisted`，并显式选择 provider / model / template。测试只使用 fake provider 或 stub response。

LLM 输出不能直接写长期记忆，必须经过：

- JSON schema validation：非法 JSON、缺少 fact type、缺少 summary、缺少 evidence 会失败。
- sanitization：Authorization、cookie、api key、token、password 等不能进入长期记忆。
- Quality Gate：低质量、太泛、无证据、敏感内容仍会被拒绝。
- Dedup / merge / conflict guard：LLM 提取出的事实也必须遵守同一套去重和身份冲突规则。

LLM-assisted 模式的错误消息也必须清洗，不能泄漏 API key、Authorization header、token 或 prompt 中的敏感片段。

### 13.7 与 V5-1 / V5-3+ 的边界

V5-1 已经提供真实 embedding provider、embedding profile、pgvector 写入和召回基础。V5-2 复用这层地基：每条长期事实进入 `LongTermMemory` 后继续写 embedding，合并后重新写 embedding，并保留 embedding profile metadata。

V5-2 不实现以下能力：

- V5-3 Memory Entity Graph：实体图谱、关系边、跨事实实体推理。
- V5-4 Query Rewrite / Multi-route Retrieval：查询改写、多路召回、按来源路由。
- V5-5 Rerank / Small-to-Big：重排、父子索引、小片段到大上下文扩展。

这些能力都依赖 V5-2 先把长期记忆写干净。如果写路径污染，再强的召回和重排都会召回噪音。

### 13.8 面试讲解版总结

ProbeFlow 的 Memory 不是日志仓库，而是 Agent 的经验提纯系统。

一次执行失败、一次人工修订、一个 SUITE 链路问题，首先会变成 Memory Candidate。Candidate 进入 `MemoryRefineryService` 后，会先被清洗，再抽取成结构化 `MemoryFact`，识别事实类型、适用范围、触发条件、证据来源和置信度。

之后系统用 Quality Gate 拒绝低价值或有污染的内容，用 fact fingerprint 和 identity hints 判断是否是已有事实，用 evidence ledger 合并重复证据，用 conflict guard 防止不同系统、模块、接口、错误码的经验互相覆盖。最终只有可复用、可追溯、可解释的事实才进入 `LongTermMemory`，并写入 embedding / pgvector，供后续 Unified Context 召回。

所以 ProbeFlow 的“学习”不是让模型记住一大段历史，而是把执行经验变成可治理的长期事实，再让后续任务按需使用这些事实。
