# 接口测试执行引擎设计文档

## 1. 文档目标

本文档定义测试 Agent 中“接口测试执行引擎”的职责、模块拆分、执行流程与技术选型。

这套执行引擎的目标不是成为一个简单的 HTTP 工具类，而是成为测试 Agent 的标准执行子系统，用来稳定完成以下工作：

- 将测试用例转换为真实请求
- 注入环境变量、动态变量与鉴权信息
- 发送 HTTP 请求
- 执行断言
- 产出标准化执行结果
- 将结果回传给编排系统、记忆系统和报告系统

---

## 2. 核心设计原则

### 2.1 执行引擎必须由本地代码实现

执行引擎建议使用本地 Java 代码实现，而不是用 AI 来完成底层执行。

原因是执行引擎需要具备：

- 稳定性
- 可重复性
- 可控性
- 低成本
- 高并发能力
- 易调试能力

因此推荐采用：

- `AI` 负责分析、规划、生成、判断
- `本地执行引擎` 负责真正执行请求和断言

### 2.2 AI 驱动执行，而不是 AI 替代执行

测试 Agent 的合理分工应为：

- AI 决定测什么、怎么测、何时执行
- 执行引擎负责把这些决策稳定落地

也就是说：

`AI 是大脑，执行引擎是手脚`

### 2.3 执行引擎是一个系统，不是一个 HTTP 工具类

执行引擎不能只是一个 `HttpUtil` 或 `ApiClient`。

它至少要包含：

- 请求构建
- 变量解析
- 鉴权注入
- HTTP 执行
- 断言执行
- 结果标准化
- 执行记录持久化

---

## 3. 与 AI Agent 的职责边界

### 3.1 AI 负责什么

AI 主要负责：

- 分析接口
- 理解业务流程
- 生成测试用例
- 生成断言建议
- 选择执行哪些 case
- 分析失败原因
- 决定是否重试、补测、结束任务

### 3.2 执行引擎负责什么

执行引擎主要负责：

- 组装 HTTP 请求
- 替换变量
- 注入认证
- 发起请求
- 执行断言
- 记录执行结果

### 3.3 典型协作流程

```text
AI 分析接口
-> AI 生成测试用例
-> AI 选择执行策略
-> Execution Engine 执行请求
-> ExecutionResult 返回
-> AI 分析结果并决定下一步
```

---

## 4. 执行引擎需要解决的问题

执行引擎至少要解决以下问题：

1. 把测试用例转换成真实请求
2. 注入环境变量、上下文变量和动态参数
3. 注入鉴权信息
4. 发起 HTTP 请求
5. 执行断言
6. 生成标准化执行结果
7. 支持单接口、批量接口、测试套件执行

---

## 5. 模块拆分建议

第一版建议将执行引擎拆成以下 8 个组件：

- `ExecutionEngine`
- `RequestBuilder`
- `VariableResolver`
- `AuthInjector`
- `HttpExecutor`
- `AssertionEngine`
- `ResultCollector`
- `ExecutionRecorder`

### 5.1 ExecutionEngine

主入口，负责协调整个执行流程。

职责：

- 接收执行任务
- 调用请求构建器
- 调用变量解析器
- 调用鉴权注入器
- 调用 HTTP 执行器
- 调用断言引擎
- 调用结果收集器
- 调用记录器

### 5.2 RequestBuilder

负责把 `ApiSpec + TestCase + ExecutionContext` 转换成最终请求对象。

职责：

- 组装 URL
- 组装 Query 参数
- 组装 Header
- 组装 Body
- 统一请求快照结构

### 5.3 VariableResolver

负责解析执行阶段的变量和动态表达式。

变量来源可包括：

- 环境变量
- 任务上下文变量
- 上一步接口输出变量
- 动态函数

### 5.4 AuthInjector

负责将认证配置注入请求。

第一版建议支持：

- Bearer Token
- API Key
- Basic Auth
- Header 注入

后续可扩展：

- 自定义签名
- OAuth 刷新机制

### 5.5 HttpExecutor

负责真正发送 HTTP 请求。

职责：

- 发起请求
- 处理超时
- 处理连接异常
- 获取响应状态码、Header、Body、耗时

### 5.6 AssertionEngine

负责执行断言，并输出结构化断言结果。

职责：

- 状态码断言
- JSONPath 断言
- Header 断言
- 文本包含断言
- 响应时间断言

### 5.7 ResultCollector

负责把原始请求/响应转换成标准化执行结果。

职责：

- 汇总请求快照
- 汇总响应快照
- 汇总断言结果
- 形成统一 `ExecutionResult`

### 5.8 ExecutionRecorder

负责执行结果持久化。

职责：

- 写入执行记录
- 写入历史快照
- 为记忆系统提供候选信息
- 为报告系统提供结构化数据

---

## 6. 主执行流程

建议主执行流程如下：

```text
ExecutionTask
-> RequestBuilder
-> VariableResolver
-> AuthInjector
-> HttpExecutor
-> AssertionEngine
-> ResultCollector
-> ExecutionRecorder
-> ExecutionResult
```

更详细一点可以表示为：

1. 读取当前要执行的接口与测试用例
2. 构建请求对象
3. 替换环境变量和动态变量
4. 注入认证信息
5. 发起 HTTP 请求
6. 获取原始响应
7. 执行断言
8. 生成标准化执行结果
9. 保存执行记录
10. 返回给编排系统

---

## 7. 核心输入对象

### 7.1 ApiSpec

表示接口定义。

建议包含：

- method
- path / url
- headers schema
- params schema
- body schema
- auth config

### 7.2 TestCase

表示测试用例。

建议包含：

- 输入参数
- 前置条件
- 断言规则
- 用例标签
- 优先级

### 7.3 ExecutionContext

表示执行时上下文。

建议包含：

- environment
- variables
- runtime options
- auth info
- previous outputs

### 7.4 ExecutionTask

表示真正待执行的任务单元。

建议包含：

- taskId
- caseId
- apiSpec
- testCase
- executionContext

---

## 8. 核心输出对象

建议统一输出 `ExecutionResult`。

建议至少包含：

- `executionId`
- `taskId`
- `caseId`
- `success`
- `requestSnapshot`
- `responseSnapshot`
- `assertionResults`
- `durationMs`
- `errorMessage`
- `statusCode`
- `observationSummary`

这个对象后续会被以下系统消费：

- 编排系统
- 记忆系统
- 报告系统

因此必须统一、稳定、可结构化处理。

---

## 9. 执行模式设计

第一版建议考虑三种执行模式：

### 9.1 SINGLE

执行一个接口测试用例。

适用场景：

- 单条验证
- 调试
- 手工触发执行

### 9.2 BATCH

批量执行一组独立接口用例。

适用场景：

- 批量回归
- Smoke 测试

### 9.3 SUITE

按顺序执行一组有关联的接口用例。

适用场景：

- 登录 -> 下单 -> 支付 这类链路测试
- 跨接口变量传递
- 多步骤验证流程

建议第一版优先支持：

- `SINGLE`
- `SUITE`

`BATCH` 可以视为多个 `SINGLE` 的并行包装。

---

## 10. 执行引擎最关键的设计点

### 10.1 请求构造与发送分离

不要把参数组装逻辑和 HTTP 发送逻辑写在一个类里。

这样后续扩展 WebSocket、gRPC、Mock 执行器时会更容易。

### 10.2 断言引擎独立

断言不属于 HTTP 发送层，而属于执行结果分析层。

因此应作为独立模块设计。

### 10.3 变量解析独立

环境变量、动态函数、链路变量都应统一进入 `VariableResolver`。

避免全项目散落字符串替换逻辑。

### 10.4 标准结果模型统一

无论成功、失败、超时、异常，都应统一输出 `ExecutionResult`。

这样编排系统不需要为不同失败类型写大量特殊逻辑。

### 10.5 单接口与套件执行共用底层执行器

不要为单接口执行和套件执行分别维护两套相似逻辑。

建议：

- 单接口执行 = 调用一次 `ExecutionEngine`
- 套件执行 = 多次调用同一个 `ExecutionEngine`

## 11. 技术选型建议

在 Java 本地执行引擎的前提下，推荐以下技术栈：

- `OkHttp`
- `Jackson`
- `Jayway JsonPath`

### 11.1 OkHttp

用于真正发送 HTTP 请求。

推荐原因：

- 稳定
- 性能成熟
- 支持连接复用
- 易于集成
- 适合作为平台底层执行器

### 11.2 Jackson

用于 JSON 序列化和反序列化。

推荐原因：

- Java 生态成熟
- 与执行结果模型集成方便
- 适合处理请求体、响应体、结果快照

### 11.3 Jayway JsonPath

用于 JSONPath 断言。

推荐原因：

- 适合做响应字段断言
- 适合平台断言层封装
- 比纯字符串断言更稳定

---

## 12. 为什么不建议用 AI 直接执行

执行引擎不建议主要依赖 AI 的原因如下：

- 执行不稳定
- 成本高
- 并发能力差
- 调试困难
- 精确断言不可靠

正确方式是：

`AI 负责生成和判断，本地代码负责执行和校验`

---

## 13. 为什么不建议用 REST Assured 作为核心执行引擎

`REST Assured` 更适合“测试脚本 DSL”，而不是平台底层执行内核。

当前平台更需要的是：

- 可控请求构造
- 统一变量替换
- 统一认证注入
- 统一执行结果模型
- 更容易嵌入编排系统

因此推荐：

- 平台执行层：`OkHttp`
- 断言层：`JsonPath + 自定义 AssertionEngine`
- JSON 处理：`Jackson`

## 15. 第一版能力范围建议

第一版建议先支持以下能力：

- HTTP `GET/POST/PUT/DELETE/PATCH`
- Query / Header / Path / JSON Body
- 环境变量替换
- Bearer Token
- 基础断言
  - 状态码
  - JSONPath
  - contains
  - header
  - response time
- 单接口执行
- 套件顺序执行
- 标准执行结果落库

第一版暂不追求：

- 多协议支持
- 极复杂自定义脚本执行
- 全自动复杂前置依赖编排

---

## 16. 一句话总结

接口测试执行引擎的核心，不是“发请求”，而是把测试用例稳定地转换为真实执行，并输出可被编排系统、记忆系统、报告系统复用的标准结果。

最终方案可以概括为：

`AI 负责决策 + 本地代码执行引擎负责请求执行 + OkHttp/Jackson/JsonPath 作为核心工具栈`
