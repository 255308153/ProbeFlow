# 测试用例生成模块设计文档

## 1. 文档目标

本文档定义测试 Agent 中“测试用例生成模块”的职责、生成流程、模块拆分与第一版落地策略。

该模块的目标是将以下输入：

- `ApiSpec`
- `UnifiedApiContext`
- `BusinessContext`
- `历史记忆`
- `项目知识库`

转换为：

- 一组可执行的 `TestCase`
- 每条用例对应的断言建议
- 前置数据建议
- 风险等级
- 覆盖标签

这套设计的重点不是“让 AI 随便写几条用例”，而是建立一套：

- 基础覆盖稳定
- 业务场景可增强
- 历史经验可复用
- 输出结构可执行

的测试用例生成体系。

---

## 2. 核心设计原则

### 2.1 规则保证基础覆盖

基础测试场景应优先由规则系统稳定生成，而不是每次都依赖大模型推理。

适合规则生成的场景包括：

- 正常请求
- 必填字段缺失
- 参数类型错误
- 边界值
- 非法枚举值
- 鉴权缺失

### 2.2 AI 补充业务深度

复杂业务场景不适合完全靠固定规则穷举，应由 AI 结合知识库、代码上下文和业务流程补充生成。

适合 AI 增强的场景包括：

- 业务规则异常
- 权限角色差异
- 幂等性问题
- 状态流转问题
- 依赖前置条件异常
- 高风险业务路径

### 2.3 记忆系统增强项目经验

用例生成不仅要看接口结构和业务上下文，还应结合长期记忆和历史失败经验补充项目级测试点。

### 2.4 输出必须可执行

该模块输出的用例不应只是“标题列表”，而应是可直接交给执行引擎的结构化测试资产。

---

## 3. 总体设计思路

测试用例生成建议采用三层生成策略：

```text
结构规则生成
+ 业务上下文增强
+ 历史记忆增强
-> 统一用例标准化
-> TestCase List
```

三层分别负责：

- 结构规则生成：保证基础覆盖率
- 业务增强生成：补足业务深度
- 记忆增强生成：补足项目经验和历史风险

---

## 4. 模块要解决的问题

该模块至少需要解决以下问题：

1. 如何从接口结构生成基础测试用例
2. 如何从业务上下文补充复杂业务场景
3. 如何从历史失败和长期记忆补充高风险场景
4. 如何为测试用例生成断言建议
5. 如何统一不同来源的 case 输出结构
6. 如何支持人工编辑与确认

---

## 5. 模块拆分建议

第一版建议将测试用例生成模块拆成以下 6 个组件：

- `CaseGenerationEngine`
- `StructureCaseGenerator`
- `BusinessCaseGenerator`
- `MemoryCaseEnhancer`
- `AssertionSuggestionGenerator`
- `CaseNormalizer`

### 5.1 CaseGenerationEngine

主入口，负责协调整个用例生成流程。

职责：

- 接收生成请求
- 调用结构规则生成器
- 调用业务增强生成器
- 调用记忆增强器
- 调用断言建议生成器
- 调用标准化输出器

### 5.2 StructureCaseGenerator

负责根据 `ApiSpec` 生成基础结构型测试用例。

这部分强调稳定与可控，不依赖运行时 AI。

核心职责：

- 识别字段约束
- 按规则生成基础 case
- 输出 `TestCaseDraft`

### 5.3 BusinessCaseGenerator

负责根据 `UnifiedApiContext` 和业务知识库生成业务场景型测试用例。

核心职责：

- 识别业务流程节点
- 识别前置依赖
- 识别高风险业务规则
- 输出业务增强 case

### 5.4 MemoryCaseEnhancer

负责根据长期记忆和历史失败经验补充项目型测试场景。

核心职责：

- 检索相关长期记忆
- 识别历史失败模式
- 输出经验增强 case

### 5.5 AssertionSuggestionGenerator

负责为每条测试用例生成断言建议。

建议覆盖：

- 状态码断言
- 响应字段断言
- 关键业务码断言
- Header 断言
- 响应时间断言

### 5.6 CaseNormalizer

负责把不同来源的 case 统一成标准 `TestCase` 结构。

这样后续执行引擎、编排系统、报告系统都可以稳定消费。

---

## 6. 主生成流程

建议主生成流程如下：

```text
ApiSpec
+ UnifiedApiContext
+ Memory
-> StructureCaseGenerator
-> BusinessCaseGenerator
-> MemoryCaseEnhancer
-> AssertionSuggestionGenerator
-> CaseNormalizer
-> TestCase List
```

更具体可以表示为：

1. 根据接口结构生成基础 case
2. 根据业务上下文补充业务 case
3. 根据长期记忆补充经验 case
4. 为每条 case 生成断言建议
5. 标准化输出结构
6. 支持人工确认与编辑

---

## 7. 基础规则生成设计

### 7.1 基础规则生成的本质

基础规则生成本质上是：

`把接口结构信息翻译成固定测试点生成规则`

它不是让模型每次“重新思考”，而是程序按规则稳定枚举场景。

### 7.2 输入要求

基础规则生成至少依赖 `ApiSpec`，包括：

- 请求方法
- 路径
- path 参数
- query 参数
- header 参数
- body 字段
- 字段类型
- 是否必填
- 枚举值
- 长度 / 范围限制
- 鉴权要求

### 7.3 规则来源与执行方式

需要明确区分两个阶段：

- 规则定义阶段：可以由人工设计，也可以由 AI 辅助设计
- 规则执行阶段：必须由本地代码稳定执行

也就是说：

`AI 可以辅助定义规则，但运行时不应依赖 AI 逐条生成基础 case`

### 7.4 规则执行方式

建议采用规则链或规则表方式：

- `generateNormalCase`
- `generateRequiredMissingCases`
- `generateInvalidTypeCases`
- `generateBoundaryCases`
- `generateInvalidEnumCases`
- `generateAuthFailureCases`

每条规则根据字段约束输出 `TestCaseDraft`。

### 7.5 ValueFactory

建议单独设计 `ValueFactory`，用于生成合法值和非法值。

例如：

- 合法 string：`test_value`
- 合法 number：`100`
- 非法 string 类型值：`123`
- 非法 number 类型值：`abc`
- 枚举非法值：`INVALID_ENUM_VALUE`
- 边界值：`min`、`max`、`min-1`、`max+1`

---

## 8. 业务增强生成设计

业务增强生成的目标不是补“结构缺口”，而是补“业务深度”。

建议重点生成以下类型：

- 业务规则异常
- 角色权限差异
- 状态流转异常
- 幂等性问题
- 重复提交
- 前置依赖不满足
- 跨步骤依赖异常

业务增强生成主要依赖：

- 知识库
- 业务流程文档
- 代码上下文
- UnifiedApiContext

---

## 9. 记忆增强生成设计

记忆增强生成主要依赖长期记忆和历史失败经验。

适合补充的场景包括：

- 某项目高频失败模式
- 某类接口常见异常
- 团队特别关注的风险点
- 历史事故复盘涉及的关键场景

这一层的价值在于让系统越用越强，而不是每个项目都从零开始。

---

## 10. 第一版建议支持的用例类型

第一版建议先固定支持以下 8 类：

- `NORMAL`
- `REQUIRED_FIELD_MISSING`
- `INVALID_TYPE`
- `BOUNDARY_VALUE`
- `INVALID_ENUM`
- `AUTH_FAILURE`
- `BUSINESS_RULE_EXCEPTION`
- `DEPENDENCY_EXCEPTION`

这 8 类已经足够支撑第一版的接口测试用例生成能力。

---

## 11. 每条 TestCase 至少需要的字段

建议每条测试用例至少输出以下字段：

- `caseId`
- `caseType`
- `title`
- `description`
- `inputData`
- `preconditions`
- `expectedStatusCode`
- `assertionSuggestions`
- `riskLevel`
- `tags`
- `source`

其中 `source` 建议区分：

- `STRUCTURE`
- `BUSINESS`
- `MEMORY`
- `MANUAL`

这样便于后续分析用例来源和生成质量。

---

## 12. 为什么不能纯靠 LLM

如果完全依赖 LLM 直接生成所有测试用例，会带来以下问题：

- 基础 case 不稳定
- 机械性关键场景容易遗漏
- 难以批量处理
- 覆盖率不可控
- 难以做规则管理与解释

因此推荐策略是：

- 结构型用例：规则生成
- 业务型用例：AI 生成
- 经验型用例：记忆增强

---

## 13. 第一版最小可用方案

第一版建议先做到：

- 从 `ApiSpec` 自动生成基础 case
- 从知识库补一个业务高风险 case
- 自动生成基础断言建议
- 支持人工编辑后再执行

这意味着第一版不是完全自动闭环，而是：

`自动生成 + 人工确认 + 自动执行`

这会更稳，更容易在真实团队里落地。

---

## 14. 与其他模块的关系

### 14.1 与接口自动分析模块

测试用例生成模块依赖：

- `ApiSpec`
- `UnifiedApiContext`

### 14.2 与记忆系统

测试用例生成模块依赖：

- 长期记忆
- 历史失败模式
- 项目知识偏好

### 14.3 与执行引擎

测试用例生成模块输出：

- 结构化 `TestCase`
- 断言建议
- 前置数据建议

供执行引擎直接消费。

### 14.4 与编排系统

编排系统负责决定：

- 什么时候生成 case
- 生成哪些接口的 case
- 是否需要在失败后补充新 case

---

## 15. Java 包结构建议

建议包结构如下：

```text
com.xxx.agent.casegen.engine
com.xxx.agent.casegen.structure
com.xxx.agent.casegen.business
com.xxx.agent.casegen.memory
com.xxx.agent.casegen.assertion
com.xxx.agent.casegen.normalize
com.xxx.agent.casegen.model
com.xxx.agent.casegen.rule
com.xxx.agent.casegen.value
```

其中：

- `rule`：负责规则定义与执行
- `value`：负责合法值 / 非法值生成

---

## 16. 一句话总结

测试用例生成模块的核心，不是让 AI 随便写几条 case，而是：

`用规则保证基础覆盖，用 AI 补充业务深度，用记忆系统增强项目经验，并统一输出可执行 TestCase`
