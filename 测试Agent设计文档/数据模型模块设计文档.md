# 数据模型模块设计文档

## 1. 文档目标

本文档定义测试 Agent / 测试平台第一版的核心数据模型，用于统一以下系统之间的数据边界：

- 工具编排系统
- 记忆系统
- 测试用例生成系统
- 接口测试执行系统
- 结果分析与报告系统

数据模型模块的目标不是一次性把所有对象都设计完，而是先定义最核心的业务对象，让第一版系统具备稳定的任务流转能力。

---

## 2. 设计原则

### 2.1 以任务为主线

测试 Agent 的整体运行过程，应该围绕 `Task` 这个主对象展开。

无论是计划步骤、测试用例、执行记录还是最终报告，都应能回溯到某个任务。

### 2.2 以执行事实为核心证据

系统不能只记录“规划过什么”，还要记录“实际执行了什么”。

因此 `ExecutionRecord` 和 `Observation` 是非常关键的事实层对象。

### 2.3 结构化优先

第一版数据模型应该优先保证：

- 可查询
- 可扩展
- 可追踪
- 可和编排系统/记忆系统稳定对接

而不是一开始就追求极端灵活的 schema。

### 2.4 为后续扩展预留空间

第一版先覆盖接口测试和用例生成主链路，但模型设计上要预留：

- UI 自动化
- 多环境回归
- 批量任务执行
- 子流程扩展

---

## 3. 核心对象总览

第一版建议先定义 7 个核心对象：

- `Task`
- `PlanStep`
- `TestCase`
- `ExecutionRecord`
- `Observation`
- `MemoryItem`
- `Report`

这 7 个对象已经足够支撑第一版测试 Agent 的主闭环。

---

## 4. 核心对象设计

### 4.1 Task

`Task` 表示一个完整测试任务，是整个系统的聚合根。

它回答的问题是：

- 这次任务在测什么
- 当前任务进行到哪一阶段
- 任务整体处于什么状态

建议字段：

- `taskId`
- `taskType`
- `taskName`
- `status`
- `sourceType`
- `sourceRef`
- `currentStage`
- `priority`
- `creator`
- `createdAt`
- `updatedAt`

建议说明：

- `taskType`：例如接口测试任务、功能用例生成任务、回归任务
- `sourceType`：例如需求文档、OpenAPI、手工输入
- `sourceRef`：原始输入来源引用，如文档 ID、接口文档地址等
- `currentStage`：当前任务处于分析、生成、执行、报告哪个阶段

### 4.2 PlanStep

`PlanStep` 表示任务执行过程中的一步，是编排系统最直接依赖的对象。

它回答的问题是：

- 当前任务被拆成了哪些执行步骤
- 每一步做了什么
- 哪一步成功，哪一步失败

建议字段：

- `stepId`
- `taskId`
- `stepType`
- `stepStatus`
- `stepOrder`
- `goal`
- `inputRef`
- `toolName`
- `retryCount`
- `startedAt`
- `finishedAt`

建议说明：

- `stepType`：如分析输入、生成用例、执行接口测试、分析结果
- `stepStatus`：如待执行、执行中、成功、失败、跳过
- `inputRef`：当前步骤使用的输入引用，如某批用例、某接口定义
- `toolName`：当前步骤最终路由到的工具

### 4.3 TestCase

`TestCase` 表示生成出来的测试用例，是测试平台的核心业务对象。

它回答的问题是：

- 具体测什么
- 怎么测
- 预期结果是什么

建议字段：

- `caseId`
- `taskId`
- `caseType`
- `title`
- `description`
- `preconditions`
- `steps`
- `expectedResult`
- `priority`
- `tags`
- `status`

建议说明：

- `caseType`：第一版可先支持功能测试用例、接口测试用例
- `steps`：建议结构化存储，而不是只放一整段文本
- `expectedResult`：建议明确到断言层，而不是只写“结果正确”

### 4.4 ExecutionRecord

`ExecutionRecord` 表示一次实际执行记录。

它回答的问题是：

- 这条用例实际是否执行过
- 在什么环境执行
- 请求与响应是什么
- 结果如何

建议字段：

- `executionId`
- `taskId`
- `caseId`
- `stepId`
- `executorType`
- `environment`
- `requestData`
- `responseData`
- `result`
- `startedAt`
- `finishedAt`
- `durationMs`

建议说明：

- `executorType`：如 HTTP、浏览器、Mock、人工执行
- `environment`：如 dev、test、staging
- `requestData` / `responseData`：建议保留结构化摘要，必要时引用原始详情存储

### 4.5 Observation

`Observation` 表示系统对某次执行结果的结构化观察。

它不是原始 response，而是对执行结果的分析层抽象。

它回答的问题是：

- 这次执行中看到了什么
- 为什么失败
- 是否存在风险
- 下一步建议是什么

建议字段：

- `observationId`
- `taskId`
- `executionId`
- `observationType`
- `summary`
- `assertionResult`
- `riskLevel`
- `failureReason`
- `nextSuggestion`

建议说明：

- `observationType`：如执行结果观察、失败归因、覆盖率补充建议
- `assertionResult`：可以进一步拆解为通过/失败断言集合
- `nextSuggestion`：可作为编排系统下一步决策的输入之一

### 4.6 MemoryItem

`MemoryItem` 表示从任务和执行过程中提炼出来的可沉淀信息。

它回答的问题是：

- 这次任务里哪些信息值得留住
- 哪些经验可以跨任务复用

建议字段：

- `memoryId`
- `memoryType`
- `taskId`
- `sourceId`
- `title`
- `summary`
- `tags`
- `importance`
- `createdAt`

建议说明：

- `memoryType`：可对应 Session、Task、Long-term 等不同层级
- `sourceId`：可关联 Observation、ExecutionRecord、Task 等来源对象
- `importance`：便于后续做优先级召回与裁剪

### 4.7 Report

`Report` 表示任务最终对用户输出的结果对象。

它回答的问题是：

- 本次任务整体结论是什么
- 执行了多少用例
- 通过/失败情况如何
- 存在哪些风险与建议

建议字段：

- `reportId`
- `taskId`
- `summary`
- `caseCount`
- `passCount`
- `failCount`
- `riskSummary`
- `findings`
- `suggestions`
- `createdAt`

建议说明：

- `findings`：用于结构化输出缺陷、异常点、风险项
- `suggestions`：用于输出修复建议、补测建议、回归建议

---

## 5. 对象关系设计

建议对象关系如下：

```text
Task
-> PlanStep
-> TestCase
-> ExecutionRecord
-> Observation
-> MemoryItem
-> Report
```

更具体地说：

- 一个 `Task` 对应多个 `PlanStep`
- 一个 `Task` 对应多个 `TestCase`
- 一个 `TestCase` 可以对应多次 `ExecutionRecord`
- 一个 `ExecutionRecord` 可以产生一个或多个 `Observation`
- `Observation` 可以提炼成 `MemoryItem`
- 一个 `Task` 最终生成一个 `Report`

---

## 6. 推荐的数据主线

第一版建议明确两条数据主线：

### 6.1 任务主线

`Task -> PlanStep -> Report`

这条主线主要服务于编排系统，表示任务怎么流转、怎么结束。

### 6.2 执行事实主线

`TestCase -> ExecutionRecord -> Observation -> MemoryItem`

这条主线主要服务于测试执行、结果分析和记忆沉淀。

这样拆开后，系统结构会更稳定，不容易把“计划”和“事实”混在一起。

---

## 7. 第一版范围建议

第一版建议优先支持以下范围：

- 接口测试任务
- 功能测试用例生成
- 接口测试用例生成
- 自动化接口执行
- 执行结果分析
- 基础报告输出

第一版可以暂时不深入的内容：

- UI 自动化复杂对象模型
- 多租户复杂权限模型
- 非结构化超大报告体系
- 复杂 DAG 子任务实例模型

## 8. 与其他模块的关系

### 8.1 与工具编排系统的关系

编排系统主要依赖：

- `Task`
- `PlanStep`
- `Observation`
- `Report`

### 8.2 与记忆系统的关系

记忆系统主要依赖：

- `Task`
- `Observation`
- `MemoryItem`

### 8.3 与测试执行系统的关系

测试执行系统主要依赖：

- `TestCase`
- `ExecutionRecord`
- `Observation`

### 8.4 与报告系统的关系

报告系统主要依赖：

- `Task`
- `ExecutionRecord`

## 9. Java 第一版落地建议

建议模块拆分如下：

```text
com.xxx.agent.model.task
com.xxx.agent.model.plan
com.xxx.agent.model.casefile
com.xxx.agent.model.execution
com.xxx.agent.model.observation
com.xxx.agent.model.memory
com.xxx.agent.model.report
```

建议第一版优先细化的三个对象：

- `Task`
- `PlanStep`
- `TestCase`

原因是：

- 编排系统最先依赖 Task 和 PlanStep
- 测试平台业务最先依赖 TestCase
- 这三个对象定下来后，后续执行和记忆对象更容易展开

---

## 10. 一句话总结

数据模型模块的目标，不是先追求完整，而是先为测试 Agent 建立稳定的任务主线和执行事实主线。

第一版建议以这 7 个对象为核心：

`Task + PlanStep + TestCase + ExecutionRecord + Observation + MemoryItem + Report`
